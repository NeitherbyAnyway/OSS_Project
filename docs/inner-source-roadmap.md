# InnerSource 도입 로드맵

## 목표와 가정

InnerSource는 조직 내부 저장소에 오픈소스 방식의 발견 가능성, 기여 절차, 리뷰와 재사용을 적용하는 운영 모델입니다. 저장소가 외부에 공개되거나 공개 라이선스로 배포된다는 뜻은 아닙니다.

이 계획은 여러 제품 팀이 공통 Git 호스팅과 이슈 추적 도구를 사용하는 조직을 가정합니다. 한 개의 공유 서비스나 라이브러리를 파일럿 대상으로 삼고, 조직의 보안·접근 통제 정책은 유지합니다.

## 운영 모델

- **후원자:** 조직 차원의 시간과 우선순위를 지원하고 장애물을 해결합니다.
- **저장소 오너:** 목적, 공개 범위, 데이터 분류, 서비스 책임자를 정합니다.
- **메인테이너:** 기여 가이드, 리뷰, 릴리스 및 유지보수 계획을 관리합니다.
- **기여 팀:** 내부 사용 사례를 제안하고 Issue와 PR로 변경을 기여합니다.
- **보안·플랫폼 담당자:** 접근 권한, 자동 검사, 비밀 정보 및 배포 경계를 확인합니다.

각 저장소에는 README, 내부 기여 가이드, 행동 강령, 코드 오너, 테스트 가능한 기본 브랜치와 명확한 유지보수 담당자가 있어야 합니다. 내부 전용 코드와 외부 공개 OSS 의존성의 라이선스·접근 정책을 혼동하지 않습니다.

## 90일 단계별 계획

### 0단계: 준비 (1~2주)

- 두 개 이상의 팀에서 반복적으로 필요로 하는 내부 라이브러리 또는 개발 도구를 후보로 고릅니다.
- 소유 팀과 후원자를 지정하고, 현재 사용자·기여 요청·리드 타임의 기준선을 기록합니다.
- 공개해도 되는 내부 범위인지 확인합니다. 고객 데이터, 비밀 정보, 규제 대상 정보가 포함된 저장소는 파일럿에서 제외합니다.
- 기여·리뷰·보안 처리 절차와 명확한 지원 채널을 마련합니다.

**통과 조건:** 저장소 오너와 메인테이너가 지정되고, 범위·보안 분류·기여 절차가 문서화됩니다.

### 1단계: 파일럿 (3~6주)

- 한 저장소를 내부 개발자 카탈로그에 등록하고 설치·사용 방법을 문서화합니다.
- 외부 팀은 Issue를 만들거나 작은 PR을 보낼 수 있게 하고, 메인테이너는 정기적인 리뷰 시간과 질문 응답 경로를 제공합니다.
- CI, 기본 브랜치 보호, 코드 오너 리뷰, 취약점 신고 경로를 설정합니다.
- 매주 첫 리뷰까지 걸린 시간, 교차 팀 기여, 반복 질문과 장애물을 기록합니다.

**통과 조건:** 파일럿 밖의 팀에서 기여가 수락되고, 메인테이너가 지속 가능한 리뷰 부담을 확인합니다.

### 2단계: 확장 (7~10주)

- 파일럿 피드백으로 저장소 템플릿, 기여 문서, 내부 검색·발견 경로를 개선합니다.
- 수요가 검증된 저장소 2~3개를 추가하고, 팀 간 기여자를 연결하는 챔피언 또는 오피스아워를 운영합니다.
- 공통 CI와 보안 기준은 템플릿으로 제공하되, 제품별 정책 변경은 저장소 오너와 협의합니다.

**통과 조건:** 새 저장소에도 같은 최소 운영 기준을 적용하고, 파일럿 팀 외의 사용과 기여가 반복됩니다.

### 3단계: 정착 및 검토 (11~13주)

- 운영 책임, 유지보수 시간, 지원 기대치와 폐기 기준을 분기별 계획에 반영합니다.
- 지표를 기준선과 비교하고, 보안·접근·리뷰 정책을 관련 담당자와 재검토합니다.
- 수요나 유지보수자가 없는 저장소는 보관·이관 또는 종료 계획을 세웁니다.

## 성공 지표

90일 파일럿의 초기 목표는 다음과 같습니다. 첫 2주 동안 기준선을 측정하고, 데이터가 목표를 왜곡하면 후원자와 함께 조정합니다.

- 파일럿 외 팀에서 온 기여가 최소 3건 수락됨
- PR의 80%가 영업일 기준 2일 안에 첫 리뷰를 받음
- 파일럿 사용 팀과 메인테이너의 만족도 및 주요 장애물이 월별로 기록됨
- 보안·라이선스·오너십 점검이 모든 파일럿 저장소에서 완료됨

단순한 PR 수보다 재사용 사례, 기여자의 대기 시간, 유지보수 부담과 보안 상태를 함께 봅니다.

## 위험과 대응

- **유지보수자 과부하:** 지원 범위와 응답 기대치를 문서화하고, 팀 간 메인테이너를 육성합니다.
- **소유권 혼란:** 최종 승인자와 서비스 운영 책임자를 분리해 명시합니다.
- **민감 정보 유출:** 내부 접근 제어를 유지하고, 코드·이슈·로그에 비밀 정보를 올리지 않도록 검사합니다.
- **기여만 늘고 유지보수가 없음:** 파일럿 시작 전에 유지보수 시간을 확보하고, 종료 기준을 정합니다.
- **내부 공개를 외부 공개로 오해:** 내부 저장소의 라이선스와 외부 OSS 배포 조건을 별도로 검토합니다.
